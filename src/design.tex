\section{\sysname Design}
\label{sec:design}

%% ================================================================
\subsection{Overview}
\label{sec:overview}
% fig:overview is defined at the end of characterization.tex so that it floats into Design.
\sysname realizes worklist-driven tiled execution: each tile takes its output coordinates from a worklist $\mathcal{W}$ of length $n_{\mathcal{W}}$, not a contiguous block, and keeps the dense reduction datapath (Figure~\ref{fig:overview}).

Because a worklist tile matches a dense tile in instructions and SM cycles
(Insight~2), what separates this selectivity from end-to-end latency reduction
are the per-layer costs of Insights~4 and~5: each construction pass takes
nearly constant time whatever the activity, and following the worklist length
requires a choice of configuration that only the device can make.
Construction (\ding{192}, \S\ref{sec:design:construct}) builds $\mathcal{W}$
from $M_{out}$ in one pass over mask metadata and, in the same kernel, selects
the tile configuration of every layer that reads $\mathcal{W}$
(\S\ref{sec:design:select}). Later operators with the same geometry reuse
$\mathcal{W}$ (\ding{193}, \S\ref{sec:design:reuse}), so neither construction
nor selection repeats at every layer. A persistent grid (\ding{194},
\S\ref{sec:design:compute}) consumes $\mathcal{W}$, reading $n_{\mathcal{W}}$
from device memory. All stages run in one per-frame CUDA graph (Figure~\ref{fig:overview}, bottom), so no host synchronization separates layers.

\subsection{Tile-Local Worklist Construction}
\label{sec:design:construct}
\label{sec:design:construct:compact}

Construction turns $M_{in}$ into $M_{out}$ and $\mathcal{W}$ in
one pass over the layer's output grid, reading and writing only mask metadata,
never features or weights (Algorithm~\ref{alg:construct}). The pass partitions
the grid into construction tiles, one per CTA. Each CTA derives its tile's
entries of $M_{out}$ by Eq.~\ref{eq:mask} (lines~3--6; a learned gate supplies them), compacts the tile's active positions in dense traversal order
(line~7), and reserves a contiguous segment of $\mathcal{W}$ with one atomic
add on $n_{\mathcal{W}}$, a counter in device memory (line~9). The buffer holds $|\mathcal{G}|$ entries, the static
upper bound on $n_{\mathcal{W}}$, so construction allocates nothing at run time
and $n_{\mathcal{W}}$ never leaves the device. Every active position lands in
exactly one segment, so the worklist is exact: $n_{\mathcal{W}}=\|M_{out}\|_0$.

\begin{algorithm}[t]
\caption{Tile-Local Worklist Construction}
\label{alg:construct}
\begin{algorithmic}[1]
\REQUIRE Input mask $M_{in}$, output grid $\mathcal{G}$
\ENSURE Mask $M_{out}$, worklist $\mathcal{W}$, length
        $n_{\mathcal{W}}=|\mathcal{W}|$
\STATE $n_{\mathcal{W}} \leftarrow 0$
\FOR{each construction tile $\tau\subset\mathcal{G}$ \textbf{in parallel}}
  \FOR{each position $p \in \tau$ \textbf{in parallel}}
    \STATE $\mathrm{active}(p) \leftarrow \exists\, r \in \mathcal{N}(p): M_{in}[r] = 1$
    \STATE $M_{out}[p] \leftarrow \mathrm{active}(p)$
  \ENDFOR
  \STATE $\mathcal{P}_\tau \leftarrow \textsc{Compact}(\tau,\,M_{out})$
  \STATE $n_\tau \leftarrow |\mathcal{P}_\tau|$
  \STATE $\mathrm{base} \leftarrow
         \operatorname{AtomicAdd}(n_{\mathcal{W}},n_\tau)$
  \FOR{each $0\le j<n_\tau$ \textbf{in parallel}}
    \STATE $\mathcal{W}[\mathrm{base}+j] \leftarrow \mathcal{P}_\tau[j]$
  \ENDFOR
\ENDFOR
\end{algorithmic}
\end{algorithm}

The resulting order is tile-local: dense within each segment, arrival order
across segments. Construction does not sort globally, which would need a
device-wide prefix scan or a second pass, because order barely affects compute (Insight~3). The pass still scans the whole grid, so its cost is
fixed by the layer shape while the convolution it enables shrinks with activity
and channel width.

\subsection{Cross-Operator Worklist Reuse}
\label{sec:design:reuse}

\sysname therefore builds a worklist only where the active set can grow. Layer
$l+1$ reuses the worklist of layer $l$ when it keeps the grid and cannot
activate a position outside layer $l$'s active set:
\begin{equation}
  \mathcal{G}^{l+1}=\mathcal{G}^{l},\qquad
  \{p \mid M^{l+1}_{out}[p]=1\} \subseteq \{p \mid M^{l}_{out}[p]=1\}.
  \label{eq:reuse-condition}
\end{equation}
The condition depends on operator types, not on mask values ($1\times1$
convolutions, activations, and normalization satisfy it), so model conversion
marks reuse edges once. A reused worklist can be a superset of the layer's
active set, so we factor the useful-compute ratio of
Eq.~\ref{eq:efficiency-framework} into a construction and a compute term:
\begin{equation}
  \eta
  = \underbrace{\frac{\|M_{out}\|_0}{n_{\mathcal{W}}}}_{\eta_{\mathrm{construct}}}
  \cdot
  \underbrace{\frac{n_{\mathcal{W}}}{|\mathcal{C}|}}_{\eta_{\mathrm{compute}}} .
  \label{eq:eta-decomp}
\end{equation}
A freshly constructed worklist has $\eta_{\mathrm{construct}}=1$. When the
upstream policy narrows a mask, as DeltaCNN's update truncation
does~\cite{deltacnn}, the reused worklist becomes a superset
($\eta_{\mathrm{construct}}<1$); the extra positions cost compute time but
not correctness, because only positions active in the layer's own $M_{out}$
are written. A new grid or a receptive field wider than one position
marks a rebuild point. Rebuild points recur at every $3\times3$ convolution, so the worklist length changes across layers as well as frames,
and the compute stage must consume a length that only the device knows.

\subsection{Worklist-Driven Tiled Compute}
\label{sec:design:compute}

Dense convolution maps to a GEMM with $M$ output positions, $N=C_{out}$, and
reduction depth $k^2C_{in}$; \sysname sets $M=n_{\mathcal{W}}$, so GEMM row $i$
is output position $\mathcal{W}[i]$, and keeps $N$, the reduction, and the
tensor and weight layouts of the dense kernel. A configuration $q$ is therefore
any point of the dense kernel's configuration space: the tile shape
$B_M\times B_N$, the reduction step $B_K$, and tiling parameters such as warp
layout, pipeline depth, and a reduction split within or across
CTAs~\cite{cutlass}.

\begin{algorithm}[t]
\caption{Worklist-Driven Tiled Compute (configuration $q$)}
\label{alg:compute}
\begin{algorithmic}[1]
\REQUIRE Input $\mathbf{x}$ on the dense grid, weights $\mathbf{f}$, output
  mask $M_{out}$, worklist $\mathcal{W}$ and length $n_{\mathcal{W}}$ in device
  memory; tile count
  $N_t=\lceil n_{\mathcal{W}}/B_M\rceil\lceil C_{out}/B_N\rceil$; $P$ CTAs
\ENSURE Output $\mathbf{y}$ at every active position
\FOR{each CTA $g=0,\dots,P-1$ \textbf{in parallel}}
  \FOR{$t=g,\,g+P,\,g+2P,\dots$ while $t<N_t$}
    \STATE $(b_m,b_n)\leftarrow$ output tile $t$
    \STATE $R\leftarrow\mathcal{W}[b_mB_M:(b_m+1)B_M]$ \COMMENT{active positions}
    \STATE $\mathbf{Y}\leftarrow\mathbf{0}_{B_M\times B_N}$
    \FOR{each receptive-field offset $i=1,\dots,k^2$}
      \FOR{each channel slice $s=1,\dots,\lceil C_{in}/B_K\rceil$}
        \STATE $\mathbf{X}\leftarrow$ load $\mathbf{x}[\mathcal{N}_i(p)]$ for $p\in R$, slice $s$
        \STATE $\mathbf{B}\leftarrow$ load $\mathbf{f}_i$, slice $s$, column block $b_n$
        \STATE $\mathbf{Y}\leftarrow\mathbf{Y}+\mathbf{X}\mathbf{B}$
      \ENDFOR
    \ENDFOR
    \STATE write $\mathbf{Y}$ to $\mathbf{y}$ at each $p\in R$ with $M_{out}[p]=1$
  \ENDFOR
\ENDFOR
\end{algorithmic}
\end{algorithm}

Because $n_{\mathcal{W}}$ exists only on the device, the host cannot launch
the right number of tiles. Algorithm~\ref{alg:compute} instead launches a
persistent grid of $P$ CTAs, sized by the configuration and the GPU alone,
which reads $n_{\mathcal{W}}$ from device memory and strides over the tiles it
implies (line~2); CTAs beyond the tile count exit immediately, so one static
launch serves every length and every frame. Each tile reads its $B_M$ worklist
entries once (line~4), and the reduction (lines~6--12) walks the kernel
offsets and channel slices as dense execution does. Because the input stays a
dense grid, each input address is a row's worklist entry plus the tap's fixed
offset: addresses inside the reduction loop stay affine, and no kernel map is
read (Insight~2). The epilogue stores only positions active in $M_{out}$
(line~13), so neither the padding of the last tile nor the superset entries
inherited through reuse are written. The padding is the only issued work
beyond the worklist:
$\eta_{\mathrm{compute}}=n_{\mathcal{W}}/(\lceil n_{\mathcal{W}}/B_M\rceil
B_M)$.

What a static grid cannot fix is the configuration itself: the fastest $q$
depends on $n_{\mathcal{W}}$ (Insight~1).

\subsection{Cost-Aware Tile Selection}
\label{sec:design:select}

Adapting the configuration to $n_{\mathcal{W}}$ costs time at every decision point
(Insight~5), so \sysname decides per layer whether, and how
finely, to follow the length by weighing the expected gain of each additional
candidate against its cost.

For layer $l$, an offline sweep on the target GPU measures the time $t_q(n)$
of every configuration $q$ in the space $\mathcal{Q}$ across worklist lengths
$n$; $t^{*}(n)=\min_{q\in\mathcal{Q}}t_q(n)$ is the per-length best. A
selection $S$ with $K$ candidates $q_1,\dots,q_K$ and thresholds
$0=\theta_0<\theta_1<\dots<\theta_K=|\mathcal{G}|+1$ runs $q_S(n)=q_k$ for
$\theta_{k-1}\le n<\theta_k$ and pays the GPU's per-layer cost of choosing
among $K$ candidates, $c(K)$ with $c(1)=0$, measured once on the same GPU.
Without a prior on the deployment's activity, the selection assumes $n$
uniform over $[1,|\mathcal{G}|]$ and maximizes the geometric-mean speedup, that
is, minimizes the expected log-slowdown relative to the per-length best:
\begin{equation}
  \hat{S}=\arg\min_{K,\,S}\ \mathbb{E}_{n}\!\left[\log
  \frac{t_{q_S(n)}(n)+c(K)}{t^{*}(n)}\right].
  \label{eq:select}
\end{equation}
Because $n$ is a scalar, the candidates partition a single range. On the
sweep's lengths $n_1<\dots<n_J$, with $L_q(u)$ the log term of
Eq.~\ref{eq:select} at $n_u$ and $w_u$ the probability mass of $n_u$'s
interval, the best expected cost $F_k(j)$ of covering the first $j$ lengths with
$k$ candidates obeys
\begin{equation}
  F_k(j)=\min_{i<j}\Big[F_{k-1}(i)+\min_{q\in\mathcal{Q}}\sum_{u=i+1}^{j}w_uL_q(u)\Big],
  \qquad F_0(0)=0,
  \label{eq:select-dp}
\end{equation}
and evaluating $F_K(J)$ for each $K$ yields $\hat{S}$ exactly. The gain of each
added candidate shrinks while $c(K)$ grows, so $K$ is an output of the
trade-off rather than a design constant.

At run time the decision must happen where $n_{\mathcal{W}}$ first exists,
without host involvement. The kernel that writes a layer's worklist learns
$n_{\mathcal{W}}$ when its last CTA finishes, compares it with the thresholds
of every layer that reads the worklist, and, before the compute launches,
switches each of these layers whose selected candidate has changed. The design
does not depend on a particular switching mechanism: $c(K)$ is the cost of the
cheapest device-side one the GPU offers (\S\ref{sec:impl}).
We measure $c(K)$ on the model's layer chain with each frame's active ratio
drawn independently, so it charges a switch whenever consecutive frames choose
different candidates, which video, whose activity is correlated across frames,
does less often; a producer that serves several reusing layers compares all
their thresholds in one epilogue. Because $K$ comes
from Eq.~\ref{eq:select}, it differs across layers, GPUs, and precisions: layers whose optimum shifts little keep
one configuration and pay nothing for selection;
\S\ref{sec:eval:ablation-sensitivity} shows that ignoring the cost loses to
this selection, and that a single well-chosen configuration comes close where
the switching mechanism costs about as much as following the length gains.
